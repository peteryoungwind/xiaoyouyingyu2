## 1. 文档目标

本文档基于现有系统能力与已有规划文档，整理出**微信小程序版本的系统需求设计方案**。本次调整后的原则如下：

1. 小程序前端页面风格要保持整体一致，建立统一视觉与交互规范。
2. 小程序前端直接调用现有 Java 后端接口，不另建独立后端。
3. 小程序要完整承接主题、学习中心、会员、卡密等核心业务。
4. 小程序需支持微信号一键登录；若使用一键登录的用户尚未注册，系统应自动完成注册。

---

## 2. 当前系统现状梳理

## 2.1 当前业务现状

现有系统已经验证了以下业务模块：

1. **主题内容系统**：话题列表、搜索、详情、标签、日历、统计。
2. **学习中心系统**：热身、词汇、表达、任务、AI 点评。
3. **会员系统**：会员有效期、卡密兑换、购买/续费引导、后台会员管理。
4. **管理系统**：主题管理、用户管理、卡密管理、AI 模型管理。

这些业务逻辑说明需求方向已经明确，小程序版本不再重新摸索业务，而是要做一套独立可运行的移动端系统与独立后端实现。

---

## 2.2 小程序技术建设原则

### 方案
- **小程序前端独立实现**
- **后端直接复用现有 Java Spring Boot 接口**
- **不另建独立后端**

### 结论
本项目实际要建设的是：

> 一套面向微信小程序的前端系统，后端直接调用现有 Java 服务接口，不重复建设后端能力。

## 2.3 现有 Java 接口资产直接复用

小程序前端直接对接现有 Java 后端已有接口，包括：

### 1. 认证接口
- `POST /api/auth/register` — 用户注册
- `POST /api/auth/login` — 用户名密码登录

### 2. 话题接口
- `GET /api/topics` — 话题列表（分页搜索）
- `GET /api/topics/{id}` — 话题详情
- `GET /api/topics/tags` — 标签统计
- `GET /api/topics/stats` — 坚持天数统计
- `GET /api/topics/calendar` — 日历视图

### 3. 学习中心接口
- `GET /api/learning/topic/{id}` — 获取学习主题
- `POST /api/learning/warmup` — 生成热身内容
- `POST /api/learning/vocabulary` — 生成词汇表
- `POST /api/learning/expressions` — 生成表达模板
- `POST /api/learning/tasks` — 生成练习任务
- `POST /api/learning/review` — AI 点评

### 4. 会员与卡密接口
- 卡密兑换通过现有接口实现（需后端配合扩展）

### 5. 微信登录扩展
微信号一键登录需在现有 Java 后端新增以下接口：
- `POST /api/auth/wechat-login` — 微信登录/自动注册

> 小程序前端不需要关心后端实现细节，只需按接口文档调用即可。

## 4. 页面风格统一设计要求

这是本次新增的明确要求，小程序前端必须形成统一设计语言。

## 4.1 统一视觉风格原则

1. **统一主色体系**
   - 主色建议延续品牌蓝色系
   - 会员权益可辅以金色/琥珀色强调

2. **统一圆角体系**
   - 卡片、按钮、输入框、弹窗采用统一圆角规范
   - 不同页面避免风格割裂

3. **统一卡片式布局**
   - 首页、主题列表、学习模块、我的页面均采用卡片化结构
   - 统一阴影、边框、留白规范

4. **统一按钮规范**
   - 主按钮：用于提交、进入学习、登录、兑换等核心动作
   - 次按钮：用于取消、关闭、切换、换一批
   - 危险按钮：仅用于删除类操作（一期用户侧尽量不出现）

5. **统一信息层级**
   - 页面主标题、模块标题、说明文字、标签、辅助文案使用固定字号层级

6. **统一图标风格**
   - 所有图标风格一致，不混用不同视觉体系

7. **统一空状态/加载状态/错误状态**
   - 空状态：统一插画或图标 + 文案 + 按钮
   - 加载状态：统一 loading 组件
   - 错误状态：统一 toast 或错误卡片

## 7. 功能需求设计

## 7.1 认证与登录

### 功能目标
支持两种登录方式：
1. 用户名密码注册/登录
2. 微信号一键登录

### 微信号一键登录规则
1. 小程序前端调用微信登录能力获取登录凭证。
2. 小程序后端与微信侧完成登录态换取与身份识别。
3. 若该微信身份已绑定系统用户，则直接登录。
4. 若该微信身份尚未注册，则系统自动创建用户并完成登录。
5. 自动注册的新用户同样享受“注册赠送 3 天会员”规则。
6. 自动注册时，系统需生成默认用户资料，并保证账号唯一性。

### 用户名密码账号与微信账号合并策略
推荐采用：`users` 主表 + `user_wechat_auth` 绑定表。

规则如下：
1. 平台以 `users` 作为唯一用户主体，一名用户只保留一条主用户记录。
2. 用户名密码登录、微信号一键登录都只是同一用户的不同登录方式。
3. 首次微信登录且系统中不存在绑定关系时：
   - 自动创建 `users` 记录
   - 自动创建 `user_wechat_auth` 绑定记录
   - 自动完成登录
4. 已绑定微信的用户再次一键登录时：
   - 直接通过 `user_wechat_auth` 找到对应 `user_id`
   - 使用同一用户数据登录
5. 已有用户名密码账号的用户，可在设置页主动绑定微信。
6. 已通过微信自动注册的用户，可后续补设用户名和密码。
7. 严禁通过昵称、用户名相似度等方式自动猜测并合并账号。
8. 同一 `wechat_open_id` 或 `wechat_union_id` 只能绑定一个用户。
9. 微信账号与用户名密码账号的合并必须通过显式绑定流程完成。

### 页面内容
1. 用户名密码登录/注册入口
2. 微信号一键登录按钮
3. 登录失败提示
4. 首次微信登录自动注册说明文案（可选）
5. 账号安全入口：支持后续绑定微信或补设用户名密码

## 8.2 微信登录后端扩展

微信号一键登录是小程序特有能力，需在现有 Java 后端新增一个接口：

### POST `/api/auth/wechat-login`

**请求体**：
```json
{ "code": "微信临时登录凭证" }
```

**响应** `200`：
```json
{
  "token": "eyJhbGciOiJIUz...",
  "username": "wx_user_xxx",
  "role": "USER"
}
```

**逻辑**：
1. 后端用 `code` 换取微信 `openid`
2. 查询 `user_wechat_auth` 表是否已绑定用户
3. 若已绑定，直接签发 token 登录
4. 若未绑定，自动创建用户 + 绑定关系 + 赠送 3 天会员，再签发 token

> 除此接口外，其余业务接口均已存在，小程序前端直接复用即可。

## 12. 结论

调整后的方案是”复用现有 Java 后端接口的小程序前端”：

> 建设一套风格统一的微信小程序前端，后端直接调用现有 Java 服务接口，仅需后端配合新增微信登录接口。

该方案最大化复用现有后端能力，降低建设成本，同时为小程序提供完整的移动端体验。
